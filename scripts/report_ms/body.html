它沒有在聽，而且可以證明

四個獨立實驗，任何一個都足以說明音訊沒有被解碼。我不是從文件推論，是直接把音訊丟進去量出來的。

1
在 data 欄位塞入「hello world」——不是合法 base64。 端點照樣回了一個正常的機率值，只算 51 tokens。 若真的解碼，這裡應該直接報錯。
2
{"type":"zzz"} 這種不存在的型別也被接受。 回傳 28 tokens，沒有任何抱怨。 state 只是被序列化成文字，type 完全沒有被驗證。
3
token 數跟著「檔案大小」長，不是跟著「音訊長度」。 0.4 秒 / 4 KB → 3,363 tokens；1.0 秒 / 19 KB → 13,880 tokens。 這是 base64 字串的文字 token，不是音訊特徵。
4
一段 10 秒的片段直接撐爆上限。 161 KB 的 base64 換算成 110,045 tokens，端點回 413 question_context_limit。 同樣的 10 秒音訊，Gemini 只要 250 tokens。

兩者的差距
所以「一樣的測試」跑不了。 不是結果不好，是輸入根本沒進去——任何從這個端點得到的「音場分類」或「發音判斷」， 都是模型在猜 base64 字串的統計特徵，沒有意義。

介面幾乎一樣，但少了一塊

noul / choice / score 三種題型、回傳的欄位、 甚至 probabilities 的語意，都與 Gemini Decisions 對得上。差別在輸入。

  "state": { "type": "text", "text": "I love this product" },
  "questions": {

    "c": { "type": "choice", "instructions": "Which?", "criteria": { "a": "A", "b": "B" } },

回應

{ "model": "microsoft-decision-1.1",
  "answers": { "q": { "type": "noul", "noul": 0.9359 } },

state 只接受單一物件（傳陣列會直接斷線）；noul 沒有 confidence 欄位； usage 沒有文字／音訊分項。

  • 錯誤型態只有一種：SSL: UNEXPECTED_EOF_WHILE_READING——伺服器在回應前直接斷線， 不是 4xx/5xx，所以一般的錯誤處理抓不到，必須當成可重試的網路錯誤。
  • 與併發無關：循序送 19 次也只有 42% 第一次成功；換成 3 個併發也一樣。
  • 重試會把延遲放大：含退避的平均值是 4.4 秒，單次成功其實只要 0.96 秒。 如果你看的是「平均延遲」，會被重試拖累而誤判成慢十倍。
  • 計價不明：回應只給 input_tokens / output_tokens 總數， 這個 deployment 的價格查不到公開資訊，因此本報告只列 token、不換算金額。

如果你要的是「微軟版的 Decisions API 來做音訊」： 這個 deployment 做不到。要嘛等支援音訊的版本，要嘛在前面接一層 ASR，把聲音轉成文字再送進來—— 但那樣就測不到發音，只剩下「內容」。

怎麼測的，以及不能推論什麼

做法

  • 先用黑箱探測還原 API 形狀（state + questions、三種題型）。
  • 音訊測試用 4 個獨立實驗確認沒有解碼，包含「非法 base64」與「假型別」兩種反向測試。
  • 文字任務與 Gemini 用同一份輸入、同一組題目、同一個門檻。
  • 每個 MS 請求最多重試 6 次（指數退避），最終失敗才記為失敗。

限制

  • 「不支援音訊」是這個 deployment 的實測行為，不代表 Microsoft 其他服務。
  • Task A 的輸入是轉錄稿，音樂／噪音片段為空字串，四成不代表模型差，是題目在文字上沒有足夠資訊。
  • Task B / C 的語料是我手寫的 18 + 24 句，標籤明確但樣本小，只能看方向。
  • 端點沒有溫度或種子參數，重跑可能不同。
